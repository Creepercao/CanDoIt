## 一、30 秒版（电梯陈述）

> 我做过一个多智能体协作平台：用户用自然语言提需求，系统由一个监督者模型把它拆成带依赖关系的执行计划，然后按依赖波次分发给不同的专业 Agent 并行执行，最后汇总成结果流式返回给前端。
>
> 技术上是一套 **LangGraph 状态图**做编排主干，节点之间用条件边做控制流，波次内部用 asyncio 并发；状态由 checkpointer 持久化，所以进程重启能续跑；再叠了一层 **RabbitMQ + Celery** 做任务派发和水平扩展，事件走 **Redis Stream**，前端可以断线续传。

**讲完这 30 秒就停，等对方发问。** 自我介绍环节不要主动展开细节。

## 二、90 秒版（对方说"详细讲讲"）

按「场景 → 难点 → 方案 → 结果」四段讲：

**场景**
> 通用大模型直接回答复杂任务是单线程的：写不了一篇文章的同时画图、同时查最新资料。我做这个平台就是把它拆成"规划 + 分工 + 汇总"，让多个专业 Agent 协作。

**难点（这句话最关键，要说得重）**
> 真正难的不是调用大模型，是三个工程问题：
> 一、**执行到一半断了怎么办**——跑十分钟的任务，进程重启或者网络断开就前功尽弃；
> 二、**该停的时候停下来**——Agent 可能被提示词注入诱导去做危险操作，必须有人在环；
> 三、**部分失败怎么办**——一个 Agent 挂了，整体不能就这样死掉。

**方案**
> 我用 LangGraph 的 StateGraph 做主流程：规划、计划审查、波次调度、执行、目标核验、补救这几个环节都是图节点，中间用条件边路由。每个节点边界都是一个 checkpoint，写进 SQLite，所以任何一个节点执行完崩掉，都能从快照恢复。
>
> 波次内部保留手写的 `asyncio.gather` 并发——这块用图反而绕，因为图节点之间是顺序语义，扇出再聚合反而要引入 Send API，不如直接把并发留在节点内部。
>
> 审批用图的 `interrupt()` 做原地挂起。这里有个坑：`interrupt()` 恢复时是**从节点第一行重新执行**，不是从断点继续。所以我把所有审批集中到一个独立的 gate 节点，每次只处理一个待审批任务，这样恢复的代价最小、也不会重放已经跑了一半的一批任务。
>
> 长任务用 RabbitMQ + Celery 派发出去，HTTP 请求只负责提交和订阅事件。事件写进 Redis Stream，每条带自增 id，前端断线重连带上最后收到的 id，就能精确补发缺失的部分。
>
> 检索侧做了三层 RAG：精确缓存、语义缓存、向量知识库。语义缓存这一层我实测过——同义改写和"同话题不同问题"的相似度分布几乎重叠，所以做成两段式判定，模糊区间必须让模型确认，确认不了就按未命中处理。知识库那边是分层检索，文档 / 章节 / 段落三级索引，先定位章节再下钻段落。

**结果**
> 全链路有 270 多项单测；端到端我用真实 broker 验过，事件序列、状态落库、断线续传都是通的。检索侧建了标注评估集，用 recall@5 和 MRR 衡量，不靠感觉调参。

## 四、高频追问与回答

### Q1：为什么不自己写循环，要用 LangGraph？

> 我一开始就是手写循环：while 循环扫任务、算波次、gather 执行。能跑，但有三个问题：
> 一是**状态恢复**要自己实现，每个位置都要手动序列化，漏一处就恢复不了；
> 二是**控制流**散在 if-else 里，加了补救回合之后，循环嵌套已经很难读了；
> 三是**可观测性**差，出了问题只能看日志。
>
> LangGraph 的价值就在 checkpoint 和显式的控制流。所以我的选择是**混合式**：控制流交给图，并发留在节点内部。不是因为图高级，是因为它恰好提供了我最缺的两样东西。

**追问：那用图有什么代价？**
> 有。图节点是顺序语义，扇出并发要绕；节点函数不能直接传参，运行时上下文得靠外部 map 传递；还有调试栈变深。但这些都是可控成本，比我手写状态机便宜。

---

### Q2：`interrupt()` 你要注意什么？

> 关键认知：**恢复时节点会从头重新执行**，不是从 `interrupt()` 那一行继续。所以节点必须是幂等的，且 `interrupt()` 之前不能有副作用。
>
> 我的做法是把审批隔离到独立节点：`gate` 节点每次只找一个还没决定的待审批任务，中断一次，记录决定，然后返回一个"待继续"的状态标记，由条件边重新进入该节点。这样每次恢复都落在一个便宜、稳定的位置。
>
> 反过来，如果把审批写在波次执行中间，恢复就会重放整波任务——可能是十分钟的重复工作。

**加分句**：这个设计我是踩过坑才收敛的，一开始把审批放在执行节点里，测试直接暴露了任务重复执行。

---

### Q3：状态持久化具体怎么做的？

> 用 LangGraph 的 checkpointer，本质是「每个 super-step 结束把整个 state 序列化写一份快照」，按 `thread_id` 归档。我用 `run_id` 作为 `thread_id`，所以一次运行就是一个可恢复的线程。
>
> 后端有三档：`sqlite`（默认，落 `outputs/checkpoints/graph.sqlite`）、`memory`（测试用）、`none`（明确不需要恢复的场景）。

**追问：为什么不直接存 JSON 文件？**
> 因为恢复不只是数据，还有**续点**——下次该从哪个节点继续。checkpointer 存的是「状态 + 待执行的节点」，这是手写 JSON 最容易漏的部分。

**追问：state 很大怎么办？**
> 会。我的 state 里有所有 Agent 的中间产物。目前的控制手段是：结果通道按类型分离，大对象落盘只存路径；预算里限制了步数和波次，避免无限增长。再往上就该做冷热分离——checkpoint 只存引用，产物进对象存储。

---

### Q4：为什么要引入消息队列？不是能跑吗？

> 能跑，但有三个硬需求：
> 一、**长任务不能绑住 HTTP 连接**。一个 PPT 生成可能几分钟，浏览器一关连接就断；
> 二、**水平扩展**。执行是 CPU 和等待混合型，多开几个 worker 能直接提吞吐；
> 三、**解耦**。API 进程不该因为跑任务被拖慢。
>
> 所以我做了开关：`MQ_BACKEND=inline` 时完全不需要 broker，本地开发和测试零依赖；`celery` 时才投递到 RabbitMQ。这样新功能不会因为要装中间件抬高开发门槛。

**追问：为什么 RabbitMQ 不是 Kafka？**
> 这是任务队列不是日志流。Kafka 的优势在保留与重放、超高吞吐；我需要的是「一条消息投给一个消费者、确认后删除」的语义，RabbitMQ 的 AMQP 模型更直接。而且 Celery 对 RabbitMQ 的支持是原生的。
>
> 如果以后要做事件溯源或者多下游消费，那 Kafka 更合适。

---

### Q5：消息不丢、任务不重复，你怎么保证？

> **不丢**：Celery 开了 `acks_late=True`，任务执行完才 ack，worker 中途崩掉消息会重新投递；`prefetch_multiplier=1` 避免一个 worker 囤一堆任务在内存里；还设了 `task_time_limit` 兜底。
>
> **不重复**：这个我要诚实说——**至少一次**语义下重复是可能的，消费端必须幂等。我的做法是：
> - 图的状态有 checkpoint，重跑会从已有快照继续，不会从头再来；
> - 任务的完成标记在 state 里，用 `_completed` 集合去重；
> - 事件流按自增 id 去重，客户端重连不会重复渲染。
>
> 严格「恰好一次」需要业务侧的唯一键 + 去重表，这个我没做到分布式事务级别。

**这段回答的价值在于主动承认边界**，面试官会认为你知道自己系统的极限。

---

### Q6：SSE 断线续传怎么实现的？

> 直觉方案是客户端重连后重新订阅，但会丢断线期间的事件。我用 Redis Stream：
> - 每个 run 一条流，`run:events:<run_id>`；
> - 每帧有自增 id（`1523456789-0` 这种）；
> - 服务端 SSE 每帧带 `id:` 字段，浏览器 `EventSource` 会自动用 `Last-Event-ID` 请求头带上最后收到的 id；
> - 服务端从那个 id 之后读，只补发缺的。
>
> 没用 Redis pub/sub，因为**pub/sub 是即发即忘的**，重连期间的消息永久丢失——这正是我要解决的问题。Stream 才有历史。

**追问：流会无限增长吗？**
> 会，所以设了上限：单 run 最多 5000 条事件，run 记录 TTL 1 小时，结束后清理。

---

### Q7：多任务并行怎么控制的？

> 调度不是预先算好拓扑排序，而是**每轮重扫所有任务**，挑出「依赖都已完成、且自己还没跑」的，作为一个波次并发执行。
>
> 这么做是因为任务集是动态的：PPT 规划完成后才知道要生成几页幻灯片，补救环节也会追加任务。预计算拓扑序做不到这一点。
>
> 并发边界由预算控制：单波步数、总步数、总波次都有上限，避免一个失控的规划把系统打爆。

---

### Q8：重试策略是怎么设计的？

> 关键是**分类**，不是无脑重试：
> - **瞬时失败**（429、超时、连接重置）→ 指数退避后原样重试；
> - **语义失败**（产出为空、格式不对、报错）→ 不重试同样的输入，而是把失败原因**追加到任务提示词**，让 Agent 自己修。这类失败退避没有意义，延迟直接设 0。
>
> 上限是双重的：单任务最多 3 次、单次运行总重试 12 次，避免一个任务把预算吃光。

**加分句**：区分这两类的收益很明显——429 你等一等就好，但 Agent 写错了代码，你等多久它还是那个错。

---

### Q9：补救（remediation）是怎么决定的？

> 目标核验环节会输出一个「完成度」判定：每条要求有没有对应的真实产物。核验不只是让 LLM 说"完成了"，而是**确定性核验 + LLM 复核**两层：
> - 确定性层检查产出物是否真实存在：要图表有没有 `chart_results`、要代码有没有执行记录；
> - LLM 层判断语义上是否真的回答了需求。
>
> 有缺口就进入补救：优先让监督者模型基于「已执行步骤 + 失败原因 + 已有产物 + 缺口」重新规划剩余步骤；模型不可用时回退到按缺口机械补齐。
>
> 补救有预算限制，默认只允许 1 轮，避免无限循环。

---

### Q10：安全层是怎么嵌进来的？

> 四个检查点，覆盖任务全生命周期：
> 1. **执行前计划审查**——整份计划的风险、破坏性意图、注入意图；
> 2. **动作门禁**——每个任务执行前判定，高风险停下来等人工审批；
> 3. **输出审查**——产物扫描凭据泄露，敏感信息替换成占位符再进状态；
> 4. **目标完成确认**——核验是否真的完成。
>
> 风险分级是 `low→放行 / medium→记一笔 / high→人工审批 / critical→直接拦`。所有判定写进**哈希链审计日志**，每条带前一条的哈希，可以用接口校验完整性。

**追问：哈希链的意义？**
> 防篡改和防删改。如果日志被中间人改了一条，后面整条链就对不上。审计场景里"日志可信"是前提。

---

### Q11：这个项目里你觉得最难的点是什么？

准备好这个答案，**这是区分背书和真做过的关键题**。推荐讲这个：

> 最难的是「审批中断」和「状态恢复」的交互。
>
> LangGraph 的 `interrupt()` 语义是恢复时重跑节点，我一开始把审批放在波次执行节点里，结果测试发现同一个任务跑了三次——因为恢复时整波重放了。这个问题非常隐蔽，表面上一切正常，只是次数对不上。
>
> 我最后是通过告警"任务被调用的次数比预期多一次"定位的。修法是把审批拆出来变成独立的 gate 节点，让每次恢复都落在一个便宜的位置。
>
> 这件事让我意识到：**状态机的正确性不能靠读代码验证，得靠可观测数据**。所以我后来把每个环节都做成了 span，父子关系、耗时、状态都记录下来，问题一眼就能定位到具体环节。

---

### Q12：如果重做，你会改什么？

> 三件事：
> 1. **前端一开始就接异步接口**。我先把后端链路做完，前端还挂在旧的长连接接口上，等于新能力的收益没兑现——这是流程上的教训，功能做完了不等于用户用上了。
> 2. **事件协议先定契约再写实现**。中间改过事件字段，前端要跟着动，成本比一开始就定死高很多。
> 3. **更早做真实环境验证**。单元测试和内存模式的集成测试都过了，但换成真实 broker 才暴露出终帧重复的问题——这类跨进程问题，本地模拟给不了信心。

---

### Q13：数据量、并发量是多少？（**小心，别编数字**）

诚实回答：

> 这是我个人项目，没有生产流量数据。我能说的是设计上的边界：预算默认单次最多 32 步、12 波，Celery worker 并发默认 2，任务超时 2 小时。
>
> 如果要评估容量，我会先压「事件写入 Redis 的吞吐」和「Agent 并发时的外部 API 限流」，这两个是瓶颈。

**绝对不要给没测过的 QPS 数字。** 面试官一追问压测方法就露馅。

---

### Q14：和 LangChain AgentExecutor / AutoGen / CrewAI 有什么区别？

> 定位不同：
> - **AgentExecutor** 是单 Agent 的工具调用循环，解决"一个 Agent 怎么用工具"；我解决的是"多个 Agent 怎么协作"。
> - **AutoGen / CrewAI** 更强调 Agent 之间对话式协商，角色扮演式协作；我这套是**规划驱动**的：先出一份明确的分步计划，再按依赖执行，可预测性更强，也更好做审批和预算控制。
>
> 我选择规划驱动是因为这个场景要"可管控"——用户要能看到"它准备做哪几步"，而不是看着几个 Agent 自由对话。

---

### Q15：为什么不用现成的编排框架，比如 Temporal / Airflow？

> Airflow 是批处理调度，面向周期任务，不适合交互式低延迟请求。Temporal 很合适——它就是做持久化工作流和幂等重试的，工程成熟度比 LangGraph 高。
>
> 我没选它主要是因为项目已经深度绑定 LangChain 生态（模型调用、消息抽象），Temporal 需要把 Activity 和我的 Agent 调用重新封装，迁移成本不划算。如果这是要上生产的商业系统，我会认真考虑 Temporal。

**这个回答展示你知道更好的方案存在，且有取舍理由。**

## 五、RAG 与检索专题（面试高频，务必准备）

### Q16：你的 RAG 是怎么做的？

> 分三层，成本从低到高：
>
> **第一层 · 精确缓存**——query 哈希直接命中，零成本。
>
> **第二层 · 语义缓存**——向量相似度找近似问题。这里我做过实测标定：**同义改写和"同话题但不同问题"的分布几乎完全重叠**（paraphrase 中位数 0.796，same_topic 中位数 0.770），所以单纯靠阈值不可靠。我改成两段式：`≥0.92` 直接命中；`0.40~0.92` 这个模糊区间必须让模型确认是不是同一个信息需求，确认失败或模型不可用一律按未命中处理——**fail-closed**。
>
> **第三层 · 知识库**——ChromaDB 持久化研究结论，跨会话可检索。

**追问：为什么不用现成的 RAG 框架？**
> 我的三层次结构里，第二层的"模型确认"逻辑框架内不好嵌，而且我需要逐层控制阈值和降级行为。框架的 retriever 抽象反而增加了绕路成本。

---

### Q17：检索层级化是怎么设计的？

> 文档层 / 章节层 / 段落层三层，每层独立建索引。
>
> 检索时先检**章节摘要**定位候选文档，再下钻到**段落 chunk**，最后按 `parent_id` 把相邻块拼回上下文喂给模型。

**追问：为什么要分层，不能直接切块吗？**
> 单层切块有对矛盾：块切小了检索准但上下文不够，块切大了上下文够但检索不准。层级化把**检索粒度**和**喂给模型的粒度**解耦了——用小块做召回，用大块做生成。

**追问：为什么不用 RAPTOR 那种递归摘要树？**
> 那需要对全库离线聚类重建摘要，成本高，而且数据一更新就得重跑。我的静态三层在摄取时就确定，增量友好。文档量级上去之后才会考虑动态摘要树。

---

### Q18：检索里你踩过什么坑？

> 一个很隐蔽的：**top_k 截断发生在阈值过滤之前**。
>
> 原实现是先向向量库要 `top_k` 条候选，再按相似度阈值过滤——结果可能返回空，而库里其实有匹配项，只是排在第 6 位被截断了。表面看是"没检索到"，实际是"取少了"。
>
> 改成先取 `max(top_k × 10, 50)` 条（上限 200），过滤完再截断到 `top_k`。

这个坑的价值在于：它说明我关注的是**召回链路**而不是只调阈值。

---

### Q19：你怎么评估检索效果？

> 建了评估集：30–50 条标注的「query → 应该命中的条目」，算 **recall@5** 和 **MRR**。
>
> 这件事的定位是前置条件——没有基线，加任何优化都是凭感觉。有了基线才能说"分层检索让 recall@5 提升了多少"，而不是"我加了分层检索"。

---

### Q20：混合检索和 rerank 做了吗？

> 都做了。
>
> **混合检索**是向量 + BM25，用 RRF（倒数排名融合）合并两路结果。理由是纯稠密向量对**专有名词、代码标识符、精确数字**很弱——这些恰恰是关键词检索的强项。两路互补。
>
> **Rerank** 用 cross-encoder（bge-reranker）对召回结果重排。向量检索是双塔模型，query 和文档各自编码、不交互；cross-encoder 让 query 和文档一起过模型，精度高但慢，所以只用在召回后的 top-N 重排上。

---

### Q21：你说的"多智能体策略学习"是 MARL 吗？

**这个必须说准确，否则会被追问训练循环和收敛曲线。**

> 不是。这是**上下文赌博机（contextual bandit）**，不是 MARL。
>
> 完整 MARL 需要联合策略网络、central critic、与可交互环境训练百万步。我这里的约束是：没有可交互环境、LLM 是黑盒、单次运行成本秒到分钟级——样本量撑不起来。
>
> 我的做法是把「任务派给哪个 agent」建模成 bandit 决策：
> - **上下文**：agent 的历史成功率、平均重试次数、依赖深度、预算余量
> - **动作**：候选 agent 集合
> - **奖励**：verification score 减去重试次数和耗时的惩罚项
> - **算法**：LinUCB 打分
>
> 冷启动阶段继续由 LLM 规划，积累几百次运行后再用策略做 A/B。

**追问：为什么不端到端强化学习？**
> 样本效率。一次运行几十秒到几分钟，收敛一个策略网络要几十万次交互，成本不可接受。上下文赌博机几百次运行就能学到有效策略，而且不需要神经网络、可解释性好。

**追问：策略会不会把系统带偏？**
> 所以接线是灰度的：先只记录「策略建议 vs LLM 实际选择」，对比预期奖励，确认不劣于 LLM 之后才开开关。奖励信号里已经包含完成度，学出"为了快而偷工减料"的策略会被惩罚项压下去。

## 六、容易被问倒的"红旗问题"清单

面试前务必自己过一遍，想清楚答案：

- [ ] worker 崩溃时，正在跑的那个任务会怎样？（→ 消息重新投递，图从 checkpoint 续；需要幂等）
- [ ] 两个 worker 同时拿到同一个 run 会怎样？（→ 需要 run 级锁或唯一约束，**想清楚你的答案**）
- [ ] 图会不会无限循环？（→ 有 `recursion_limit`，默认 200）
- [ ] 审批人一直不点怎么办？（→ 超时 fail-closed，按拒绝处理，默认 600 秒）
- [ ] 预算耗尽时系统怎么表现？（→ 发 `budget_exceeded` 事件，带上耗尽原因，优雅收尾而不是崩）
- [ ] 事件丢了客户端会卡住吗？（→ 有心跳帧保活，30 秒一次）
- [ ] 怎么防止 Agent 被提示词注入操控？（→ 输入筛查 + 不可信内容围栏 + 高风险动作必须人工确认）
- [ ] 为什么用 SQLite 存 checkpoint 而不是 PostgreSQL？（→ 单机部署零依赖；多实例要换 PostgreSQL，读写并发不够）

## 八、备用的"一句话总结"
